## 6. Alerts

### 🔴 ALERTA — Runtime bloqueado (Docker)
El estado del sistema registra Docker daemon sin conexión al engine `dockerDesktopLinuxEngine`. Esto bloquea el Postgres local (puerto 5435 dev / 5434 test), el Mailhog (8025/1025), y cualquier ejecución local de la API. Sin postgreSQL local, no hay `make dev`, no hay scheduler, no hay workers.

**Impacto:** cero actividad de scraping, enriquecimiento, envío, seguimiento ni lectura de inbox esta semana.

### 🔴 ALERTA — Sin credenciales de servicio en workspace
`SERVICE_TOKEN_KEY`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SERVICE_TRUSTED_CLIENT_IDS`, `PUBLIC_BASE_URL` y `FRONTEND_BASE_URL` están en Vercel pero **no persistidos en el workspace** (`.env.local` los tiene como `[SENSITIVE]`). Por eso:
- No se puede firmar un token HMAC válido para consultar las métricas.
- No se puede ejecutar Hermes (dispatch requiere `hermes.dispatch` + token firmado).
- No hay forma de generar el reporte desde la API y no desde el runtime local.

### 🔴 ALERTA — Scheduler deshabilitado en Vercel
`SCHEDULER_ENABLED=false` en el entorno de producción despliegue. El scheduler interno (follow-up tick cada 15 min, inbox sync cada 10 min) no corre. Si se quiere actividad automática, requiere:
- Habilitar `SCHEDULER_ENABLED=true` **en una sola instancia** (documentación explícita: si hay dos instancias con scheduler activo, los ticks se duplican).
- O configurar cron externo: Vercel Cron (`/cron/followup-tick`) o systemd timer (self-hosted).

### 🔴 ALERTA — Sin cuenta de correo configurada
El módulo de email requiere SMTP o OAuth (Gmail/Microsoft). Sin cuenta, no hay posibilidad de enviar, ni de sincronizar respuestas. El formulario del sitio público (`veyrasoluciones.com/api/lead`) está en modo REVIEW — acepta el lead pero no envía email ni lo escribe a producción.

### 🟡 AVISO — Backend de cola en proceso
`JOB_QUEUE_BACKEND=inprocess` (InProcessQueue, asyncio). Funciona para MVP y una sola instancia; no escala a múltiples workers ni sobrevive a reinicios. El documento de operación marca explícitamente que cuando el volumen lo pida, migrar a `arq` + Redis requiere cambiar una línea en `app/core/container.py`.

### 🟡 AVISO — Frontend sin tests
El frontend de Mapache (13 pantallas) no tiene tests unitarios ni de integración registrados. El backend sí (737 tests totales).

## 7. Recomendaciones

### R1 — Prioridad 1: Habilitar runtime local (esta semana)
- Verificar/reconectar el engine de Docker Desktop (linux engine).
- `cd backend && make up && make migrate && make dev`.
- Levantar la API en localhost:8000 y confirmar que `/health/ready` devuelve `database: ok` desde local.
- Sin esto no hay nada más que hacer.

### R2 — Prioridad 1: Descargar y persistir variables SENSITIVE
- Desde Vercel CLI o panel: exportar `SERVICE_TOKEN_KEY`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `PUBLIC_BASE_URL`, `FRONTEND_BASE_URL`, y `SERVICE_TRUSTED_CLIENT_IDS` al workspace (ej. `.env.local` extendido o gestor de secretos).
- Con `SERVICE_TOKEN_KEY` en el workspace, se puede generar un token HMAC firmado y consultar `/api/v1/metrics/overview` y `/api/v1/metrics/funnel` desde Hermes.
- Guardar `SERVICE_TOKEN_KEY` fuera del repo (ya está en `.env.local` como `[SENSITIVE]`, solo falta preservar el valor real).

### R3 — Prioridad 2: Ejecutar primer ciclo de descubrimiento
Una vez que la API esté corriendo localmente:
1. Crear un servicio de prueba (ej. consultoría comercial, o el servicio que se quiera vender).
2. Crear búsqueda con proveedor `google_maps_scraper` o `google_places_api`.
3. `POST /searches/{id}/run` → job `DISCOVERY` → company rows → `ENRICHMENT` → `SCORING`.
4. Verificar que `/metrics/overview` devuelve empresas, leads y actividad real.

**Nota:** ejecutar solo con `DISCOVERY`, `ENRICHMENT` y `FOLLOWUP_TICK` — nunca `SEND_BATCH` desde Hermes (bloqueo deliberado).

### R4 — Prioridad 2: Configurar cuenta de envío
- Empezar con SMTP si no hay OAuth configurado.
- Verificar SPF/DKIM/DMARC en el dominio de envío **antes** del primer envío.
- Respetar la curva de warm-up (20 → 100 emails/día en 22 días).
- El endpoint `GET /settings/oauth-providers` devuelve lista vacía mientras no haya credenciales; la interfaz debe ofrecer solo SMTP en ese caso.

### R5 — Prioridad 3: Conectar Hermes como agente programado
- Con `SERVICE_TOKEN_KEY` disponible, generar token HMAC (`hermes` client id, scopes mínimos `hermes.dispatch + hermes.jobs.read`).
- Configurar cron que dispare `DISCOVERY` semanalmente sobre búsquedas activas y `FOLLOWUP_TICK` frecuente.
- El token requiere refresco por TTL (5 minutos por defecto) o clock skew — diseñar regeneración automática.

### R6 — Prioridad 3: Habilitar scheduler en Vercel o pasar a cron externo
- Si el deployment de Vercel puede ejecutar el scheduler interno (single instance), set `SCHEDULER_ENABLED=true` y verificar que no hay segunda instancia.
- Alternativa recomendada para producción estable: Vercel Cron (`/cron/followup-tick` cada 15 min, `/cron/scraper-health` diario 08:00) + systemd timer si es self-hosted.

### R7 — Prioridad menor: Persistir estado semanal
- Crear `memory/` en el repo (o fuera, donde sea persistente) y escribir `state.json` con contadores semanales y `report_YYYYMMDD.txt`.
- Esto da un historial acumulativo y evita depender solo de memoria episódica.
- Dado que no hay runtime con datos, el primer reporte es manual. A partir de la primera actividad real, el reporte debe generarse consultando `/metrics/overview`, `/metrics/funnel`, `/metrics/attention`, `/metrics/leads-timeseries` y `/api/v1/leads/segments/summary`.
